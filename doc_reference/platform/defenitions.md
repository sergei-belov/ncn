## Основные сущности и понятия

Платформа **QAi** строится вокруг набора логически связанных сущностей, каждая из которых играет ключевую роль в процессе автоматизированного тестирования. Ниже приведены основные понятия и их функциональные особенности.

---

### 🔹 Проект

Базовая единица, в рамках которой осуществляется настройка, генерация и запуск автотестов для определенного веб-приложения.

**Содержит:**

* ссылку на тестируемое приложение;
* переменные (`variables`) и секреты (`secrets`);
* граф проекта с нодами, состояниями, command steps, href-кандидатами и request diff;
* графы действий;
* тест-кейсы и их версии;
* AI generation session'ы, preview и trace генерации;
* отчёты и историю запусков.

Проекты могут использовать переиспользуемые действия и графы, а также масштабироваться для командной работы.

---

### 🔹 Переменные и секреты

Используются для настройки тестовой среды.

* **Переменные** — параметризованные значения, такие как URL, идентификаторы, названия объектов, ожидаемые значения.
* **Секреты** — защищённые данные (пароли, ключи API, токены), используемые только внутри тестов и хранимые в зашифрованном виде.
* В AI-generation агент получает только **метаданные** переменных и шаблоны вида `{{Variable}}`, но не должен получать секретные значения.

---

### 🔹 Граф действий (Action Graph)

Визуальное представление пользовательского сценария в виде набора связанных **действий (actions)**. Граф создается в drag-n-drop-интерфейсе, с участием LLM-модели, которая по описанию пользователя подбирает код для выполнения действия.

**Особенности:**

* Один вход на каждое действие, допускаются множественные выходы (ветвления).
* Поддерживаются позитивные и негативные сценарии.
* Графы и отдельные действия могут переиспользоваться между проектами или использоваться как предусловия в других тестах.

---

### 🔹 Граф проекта (Project Graph)

Проектный граф - это информационная модель тестируемого приложения внутри одного проекта. Он описывает страницы или экраны, состояния DOM, команды браузера, href-кандидаты, request diff и правила URL-нормализации.

**Ключевое правило:** source of truth для достижимости — это цепочка `graph_command_steps`. Связность графа определяется `graph_command_steps.before_step_id`; состояния являются результатом команд через `graph_states.command_step_id`, а edges/request summaries вычисляются сервисами.

**Особенности:**

* У каждого проекта есть один граф проекта.
* У графа есть одна стартовая нода после инициализации.
* Граф сам по себе не запускает тесты и не заменяет пайплайны.
* В текущем этапе граф не меняет pipeline editor, run UI и execution flow.

---

### 🔹 Нода графа (Graph Node)

Нода графа представляет страницу, маршрут или экран тестируемого приложения.

**Содержит:**

* исходный URL;
* нормализованный URL-шаблон для отображения;
* полный route regex pattern для backend-сопоставления;
* параметры маршрута и настройки нормализации;
* описание страницы;
* набор состояний, если они уже были получены.

Нода может существовать без состояний, например если она создана вручную. Href-навигация подтверждает достижимость через обычный command step: `page.goto(resolved_href)` или валидированный click по ссылке.

---

### 🔹 Состояние графа (Graph State)

Состояние графа - это конкретное очищенное DOM-состояние ноды.

Примеры:

* начальное состояние страницы;
* открытое модальное окно;
* открытая боковая панель;
* результат поиска;
* список с созданным объектом.

Состояние всегда принадлежит одной ноде и всегда ссылается на командный шаг, который его породил. Хэш очищенного DOM используется для сравнения и восстановления, но не является основной связью графа.

---

### 🔹 Командный шаг графа (Graph Command Step)

Командный шаг графа описывает одну выполненную браузерную команду и является source of truth для связности графа.

**Содержит:**

* before URL / node / state;
* прямую валидированную Playwright-команду;
* phase (`positioning`, `agent`, `recovery`, `manual`, `href_discovery`, `system`);
* request diff, возникший во время команды;
* after URL / node / state;
* статус и metadata.

Именно command step отвечает на вопрос: "какой командой мы перешли из одного состояния в другое".

---

### 🔹 Request diff командного шага

Request diff — это список network requests, зафиксированных во время выполнения конкретной команды. Он не должен нарастать на каждом состоянии.

Правильная модель:

```text
command: click Login
requests diff: POST /login, GET /select-project, GET /api/projects
```

Неправильная модель:

```text
State C requests = requests from A + B + C
```

---

### 🔹 Navigation projection

Command graph не является последовательным списком: переходы строятся по `before_state_id -> after_state_id`, поэтому одна state может иметь несколько исходящих command steps или не иметь их вовсе. `trace_seq` нужен только для отображения конкретного runtime trace.

Navigation projection описывает достижимость между нодами и строится из command steps. В отличие от старой модели, таблица navigation edges не должна уничтожать реальные observed transitions только потому, что они не входят в shortest path.

Shortest path — это metadata/projection для layout и восстановления, а не единственная сохраняемая связность.

---

### 🔹 State relation projection

State relation projection описывает достижимость между состояниями и строится из command steps.

Backend-модель остается state-oriented на уровне projection, но source of truth — command step:

```text
source_state -- command_step --> target_state
```

---

### 🔹 Graph Builder Agent

Graph Builder Agent строит граф проекта через навигацию по тестируемому приложению. Он работает относительно текущей ноды и текущего состояния, ищет уже известные ноды/состояния, открывает страницы, выполняет команды и записывает command steps.

**Пример начального исследования:**

```text
User: перейти на главную страницу проекта
Agent: открывает стартовую ноду и видит экран авторизации
User: введи логин и пароль, используй {{Login}} и {{Password}}
Agent: выполняет fill login, fill password, click login как отдельные command steps
System: строит projection auth -> select project из command steps
```

**Пример поиска по графу:**

```text
System: стартовая страница - Monitoring
User: перейди в service history, в группу областей с линейными графиками
Agent: ищет подходящее состояние в графе, проигрывает известные command steps как recovery и открывает нужное состояние
```

**Пример Playwright codegen:**

```text
User: отправляет Playwright codegen
Agent: использует код как guidance, но backend выполняет только валидированные команды по одной
```

Агент не создает пайплайны, шаги, тест-кейсы, запуски и не исполняет загруженный Playwright codegen напрямую в рамках Step 07.

---

### 🔹 Действие (Action)

Ключевая единица графа, представляющая конкретное пользовательское действие. Каждое действие:

* создаётся на основе описания пользователя с помощью LLM или через AI-assisted refinement;
* имеет связанный фрагмент **абстрактного кода**;
* может быть частью позитивного или негативного сценария;
* содержит **набор проверок** (может быть пустым);
* включает **статус выполнения** (успешно / с ошибкой / не выполнено / выполняется);
* **автоматически связывается со скриншотом** или HTML-контекстом, полученным при исполнении/анализе шага.

---

### 🔹 Проверка (Assertion)

Внутри действия может быть одна или несколько **проверок** — условий, которые должны быть выполнены после действия.

**Каждая проверка включает:**

* описание (например, "Элемент .dashboard должен быть видим");
* статус (пройдена / провалена / не выполнена);
* тип сравнения (наличие элемента, текст, значение атрибута и т.п.);
* контекст действия, в котором она выполнялась.

---

### 🔹 Абстрактный код

Промежуточное представление сценария, полученное на основе графа действий. Оно пригодно для генерации реального тестового кода с помощью LLM (в текущей версии — для Playwright).

Это представление может быть:

* создано пользователем вручную;
* получено при запуске отдельного шага;
* предложено AI-generation агентом внутри preview до сохранения.

---

### 🔹 Тест-кейсы

Тест-кейс в QAi строится вокруг **пайплайна**, который является редактируемым черновиком сценария. Из этого черновика публикуются **версии тест-кейса**, которые затем используются для запуска и истории изменений.

Тест-кейс включает:

* основную последовательность действий;
* стартовые предусловия (указанные действия из других графов);
* ожидаемые результаты;
* связанный код и статусы проверок;
* опубликованные версии для стабильного запуска и отката.

---

### 🔹 Черновик тест-кейса (Pipeline Draft)

Черновик — это **редактируемое состояние** тест-кейса. Именно в нем пользователь:

* меняет структуру графа;
* добавляет и удаляет шаги;
* редактирует проверки;
* меняет описание, теги и зависимости;
* вставляет ссылки на переменные вида `{{BASE_URL}}`.

Черновик может отличаться от последней опубликованной версии. Это нормально и является основой рабочего процесса.

---

### 🔹 Версия тест-кейса (Pipeline Version)

Версия тест-кейса — это **неизменяемый снимок** опубликованного черновика. Она фиксирует:

* метаданные пайплайна;
* набор шагов;
* связи между шагами;
* проверки;
* зависимости pre/post pipelines;
* метаданные использования переменных.

В опубликованной версии сохраняются ссылки и метаданные переменных, но не копируются секретные значения и runtime-значения переменных.

После публикации версия не редактируется. Если сценарий нужно изменить, пользователь возвращается к черновику и публикует новую версию.

---

### 🔹 Активная версия

Для каждого тест-кейса в проекте выбирается **одна активная опубликованная версия**.

Именно активная версия:

* используется при запуске тест-кейса;
* показывается в списке пайплайнов как текущая версия;
* может быть переключена на более старую версию для отката.

При этом переключение активной версии **не переписывает черновик**. Черновик и активная версия существуют параллельно.

---

### 🔹 AI Generation Session

AI Generation Session — это **асинхронная сессия генерации**, которая запускается пользователем из списка пайплайнов, редактора пайплайна или сайдбара шага.

Сессия:

* относится к одному проекту;
* может быть связана с конкретным pipeline или step;
* хранит исходный запрос пользователя, статус и настройки генерации;
* выполняется асинхронно через Kafka и LangGraph worker;
* может содержать несколько preview-результатов.

Сессия сама по себе не меняет draft-таблицы, а только управляет генерацией и review flow.

---

### 🔹 Preview генерации

Preview — это **нормализованный черновой результат**, который агент сгенерировал до сохранения в доменную модель.

Preview может описывать:

* создание нового pipeline draft;
* patch текущего pipeline draft;
* patch конкретного шага;
* добавление следующих шагов после выбранного шага.

Preview содержит:

* pipeline metadata;
* steps;
* `steps_links`;
* assertions;
* suggested variables.

Пользователь может:

* принять preview;
* вручную отредактировать preview;
* отклонить preview;
* запросить новую генерацию в рамках той же session.

---

### 🔹 Trace сообщений агента

Во время AI-generation система сохраняет сообщения planner, QAi agent, validator и tool-вызовов.

* В UI показывается **сокращенный trace**.
* В БД сохраняется **полный trace** для аудита и дебага.
* Сообщения читаются через polling endpoint по `seq_no`, а не по offset, чтобы корректно работать с растущим журналом.

---

### 🔹 Результаты тестов

Для каждого прогона теста фиксируются:

* статус выполнения (успешно / с ошибками);
* версия тест-кейса, которая была выбрана для запуска;
* результаты по шагам и проверкам;
* **скриншоты на каждом шаге**;
* логи выполнения;
* информация о прохождении через ветвления (если применимо).

---

### 🔹 Модель (LLM)

LLM отвечает за:

* интерпретацию текстовых описаний действий от пользователя;
* анализ HTML-разметки целевой страницы (как контекст);
* генерацию абстрактного кода и его трансформацию в готовый автотест;
* участие в цепочке planner → QAi agent → validator для AI-generation preview.


### 🔹 Финальное правило Project Graph

Связь команд задаётся через `before_step_id`. Состояние задаёт результат команды через `command_step_id`. Нода задаёт URL/route-группировку для состояния через `node_id`. Сессия хранит только `current_state_id`; текущий command step вычисляется из состояния.
