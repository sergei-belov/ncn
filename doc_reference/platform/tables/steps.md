# Steps Table

## Description
The `steps` table contains individual test steps within pipelines, representing specific user actions or validations in automated test scenarios. Each step corresponds to a node in the visual action graph.

## Schema

| Column | Type | Constraints | Default | Description |
|--------|------|-------------|---------|-------------|
| id | UUID | PRIMARY KEY | gen_random_uuid() | Unique identifier for each step |
| name | VARCHAR(100) | NOT NULL | - | Name or title of the step |
| description | TEXT | NULLABLE | - | Detailed description of what the step does |
| case | TEXT | NOT NULL | - | Test case description associated with the step |
| html | TEXT | NULLABLE | - | Captured HTML content or relevant page fragment associated with the step |
| pipeline_id | UUID | FOREIGN KEY (pipelines.id) ON DELETE CASCADE, INDEX | - | Reference to the parent pipeline |
| code | JSONB | NULLABLE | {} | Abstract code representation generated by LLM |
| meta | JSONB | NULLABLE | {} | Frontend/editor metadata such as `position` and `locked` |
| status | VARCHAR(15) | NOT NULL | 'redacting' | Current status of the step: `redacting`, `success`, or `failure` |
| created_at | TIMESTAMP | NOT NULL | NOW() | Timestamp when the step was created |

## Relationships
- **Many-to-One**: Belongs to a pipeline via `pipeline_id`
- **One-to-Many**: Contains multiple assertions via the `assertions` table
- **Self-referencing**: Connected to other steps via the `steps_links` table
- **Graph Rule**: A step with no incoming `steps_links` record is treated as a start step in the editor. A non-start step may have one incoming link and many outgoing links.

## Purpose
Steps represent the atomic units of test execution, containing the specific actions and validations that make up automated test scenarios, along with their execution status and generated code.

## Editor Metadata
The pipeline redactor stores UI-only step settings inside `meta`:

- `position`: canvas coordinates for Vue Flow rendering
- `locked`: whether the step can be moved on the canvas

Start-step state is not stored as a separate column or `meta` flag. It is derived from graph structure: no incoming link means the editor renders the step without an input handle.

## Readiness Mapping
The editor readiness badge is derived from `status`:

- `success`: ready
- `redacting`: not ready
- `failure`: not ready

# Assertions Table

## Description
The `assertions` table contains validation checks associated with individual steps, defining conditions that must be met for the step to be considered successful.

## Schema

| Column | Type | Constraints | Default | Description |
|--------|------|-------------|---------|-------------|
| id | UUID | PRIMARY KEY | gen_random_uuid() | Unique identifier for each assertion |
| name | VARCHAR(100) | NOT NULL | - | Name or title of the assertion |
| description | TEXT | NULLABLE | - | Detailed description of what the assertion validates |
| step_id | UUID | FOREIGN KEY (steps.id) ON DELETE CASCADE, INDEX | - | Reference to the parent step |
| code | JSONB | NOT NULL | {} | Code representation of the assertion condition |

## Relationships
- **Many-to-One**: Belongs to a step via `step_id`

## Purpose
Assertions define the specific validation points within each step, ensuring that expected conditions are met during test execution and contributing to the overall pass/fail status of the test.

# Steps Links Table

## Description
The `steps_links` table establishes connections between steps, creating directed relationships that define the sequence and flow of execution in a test scenario.

## Schema

| Column | Type | Constraints | Default | Description |
|--------|------|-------------|---------|-------------|
| id | UUID | PRIMARY KEY | gen_random_uuid() | Unique identifier for each link |
| upstream | UUID | FOREIGN KEY (steps.id) ON DELETE CASCADE, INDEX | - | ID of the preceding step in the flow |
| downstream | UUID | FOREIGN KEY (steps.id) ON DELETE CASCADE, INDEX | - | ID of the succeeding step in the flow |

## Relationships
- **Many-to-One**: References the `steps` table twice - once for the upstream step and once for the downstream step

## Purpose
Steps Links define the execution flow between individual steps, allowing for branching and conditional logic in test scenarios, similar to edges in a directed graph.

## Graph Constraints
- `downstream` should not already have another incoming link unless an explicit reconnect operation replaces that link.
- Multiple links may share the same `upstream` step to represent branching scenarios.
- Deleting a step through the redactor API removes connected links and step assertions as part of the screen contract.
