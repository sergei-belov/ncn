# Часть II. Архитектурные компоненты

## 5. Компоненты MVP

### 5.1 `agent-core`

Единый backend-сервис MVP. Отвечает за:

- API управления агентами, Sessions и Runs;
- проверку project isolation, ролей и permissions;
- сбор контекста;
- запуск и сопровождение Temporal Workflow;
- выполнение coordinator/worker invocation;
- планирование и валидацию плана;
- вызов MCP;
- Approval;
- сохранение состояния, событий и usage;
- работу с памятью и артефактами.

Внутри сервиса должны сохраняться модульные границы, позволяющие позднее выделять компоненты без изменения внешней семантики.

### 5.2 Temporal

Temporal управляет жизненным циклом Run и является механизмом durable orchestration.

Temporal хранит ход исполнения, но не является источником истины для пользовательского business state. Состояние, необходимое API, аудиту, аналитике и восстановлению продукта, сохраняется в PostgreSQL.

### 5.3 PostgreSQL

PostgreSQL является первичным хранилищем конфигурации, Run state, Approval, usage, audit metadata и ссылок на артефакты.

Транзакционные границы и ограничения целостности должны предотвращать cross-project access и повторное применение локальных команд.

### 5.4 Qdrant

Qdrant используется как производный поисковый индекс для RAG. Потеря или пересоздание индекса не должна приводить к потере первичных данных.

### 5.5 MinIO/S3-compatible storage

Объектное хранилище содержит исходные и производные артефакты. PostgreSQL содержит metadata, ownership и lifecycle state.

### 5.6 MCP

MCP является основной границей между агентным ядром и доменными инструментами. Агент не получает прямой доступ к базе доменного сервиса.

# Часть III. Модель агентов

## 6. Координатор

В каждом Project существует ровно один активный координатор.

Координатор:

- интерпретирует пользовательскую цель;
- определяет необходимость уточнения;
- выбирает работников;
- строит и изменяет ещё не выполненную часть плана;
- агрегирует результаты;
- принимает семантические решения;
- инициирует tool calls и Approval;
- формирует итоговый результат.

Координатор не может обойти backend validation, project constraints, permission policy, Approval policy или platform limits.

## 7. Работник

Работник является специализированным Project-scoped агентом.

Работник:

- получает ограниченный контекст и задачу от координатора;
- использует только назначенные ему tools и memory scopes;
- возвращает структурированный результат координатору;
- может инициировать разрешённые tool calls через `agent-core`.

Работник не может:

- запускать другого работника;
- создавать отдельный Run;
- изменять план Run;
- расширять собственные permissions;
- отключать Approval;
- менять Project scope.

## 8. Конфигурация и версии

Редактируемая конфигурация агента и конфигурация, использованная в Run, должны быть разделены.

При запуске Run создаётся неизменяемый snapshot как минимум следующих данных:

- системные и пользовательские instructions;
- модель и основные model parameters;
- разрешённые MCP servers/tools;
- permission/approval policy;
- memory configuration;
- применимые project constraints.

Изменение агента после старта Run не меняет уже выполняющийся Run.

Точный формат сущностей конфигурации определяется при проектировании схем данных.
